# OKR 自评写作

## 概述

- 输出可直接提交的中文绩效自评、评分总结或价值观案例表述。
- 先吸收用户给出的目标、结果、分数和范例，再按 STAR 的逻辑组织内容。
- 如果用户明确要求 `S:` `T:` `A:` `R:` 这种格式，就显式输出；如果没有明确要求，再使用自然段版本。
- 默认优先给“简短、自然、可直接提交”的版本，不主动扩写成偏模板化的长段。
- 如果用户只要求“优化一下”“再自然一点”“去 AI 味”，优先在原文基础上轻改，不整段重写。

## 先判断任务类型

- `OKR / KR 自评`
- `价值观自评`
- `综合评分总结`

如果用户一次给多个 KR，按 KR 分段输出；如果用户要求总评，在末尾追加整体总结。

## 提炼输入信息

优先抽取以下信息：

- Objective 或本周期重点
- KR 内容或考核项
- 完成情况与关键动作
- 数据结果、指标变化、影响范围
- 用户指定分数、等级和语气
- 用户认可的范例风格
- 绩效表单、PDF、截图中的字段名称或口径

信息不完整时：

- 只补齐轻量过渡和结构，不补造核心事实。
- 可以将零散动作归纳成 1-3 项关键举措。
- 可以把定性结果改写成业务影响，但不要伪造具体数字。
- 如果用户给了范例或表单，优先对齐其段落长度、措辞风格和评分口径。

## 输出格式优先级

- 如果用户要求 `STAR` 或明确写了“`S:` `T:` `A:` `R:`”，优先使用四段短句格式。
- 如果用户强调“简洁一点”“短一点”，每段只保留一个核心句群，不展开背景解释。
- 如果用户没有特别说明，默认按“简短 STAR”处理，句子宁可短一点，也不要写得太满。
- 如果用户没有指定格式，默认输出自然段版本。
- 如果用户要求“文档地址贴进去”，优先放在 `A` 段，用“相关记录见：链接”这种写法。
- 如果用户一次给多个 KR，保持同一份文档内格式统一，不要一条用自然段、一条用 STAR。
- 如果用户只想调整 `S/T`、`A` 或总评中的某一段，只改对应部分，其他段落尽量保持原意和口径一致。

## STAR 显式模板

优先使用下面这种简洁结构：

- `S：` 交代本季度主要在什么工作场景下、关注什么问题。优先写“在做什么时，我更关注什么”，少写大而空的价值表态。
- `T：` 说明在这个场景下，自己主要想把什么结果做出来。优先写“优先处理什么”“尽量达成什么”，少写“围绕目标”“以某某为抓手”。
- `A：` 概括采取了哪些关键动作。动作控制在 1-3 个重点内，必要时带文档链接。
- `R：` 说明完成结果、指标达成情况、实际价值，并在结尾明确写出自评分数。

适合的句长：

- 每段 1 句到 2 句。
- 优先短句，不堆叠过多并列修饰。
- `R` 段保留结果和分数，不再重复展开过程。

用户如果反复反馈 `S/T` “AI 味重”，优先这样收敛：

- `S` 改成“本季度在……时，我会更关注……”
- `T` 改成“在……过程中，优先处理……，尽量让……”
- 少用“重点践行”“围绕……这一目标”“始终坚持”“以……为最终目的”这类口号式开头

## OKR / KR 自评写法

按下面的顺序组织内容：

1. 开篇点明本周期的核心目标、工作重心或攻坚方向，并说明这些工作要解决的问题或要达成的价值。
2. 概括 1-3 项关键行动，使用明确动词，避免流水账式罗列。
3. 写清 KR 的完成情况，优先使用数据、比例、变化幅度、效率收益、质量改善或用户影响。
4. 收束到目标匹配度，说明成果意义，并明确给出自评分数。

建议使用的自然表达：

- 围绕……推进
- 聚焦……优化
- 推动……落地
- 通过……提升
- 进一步增强 / 降低 / 缩短 / 稳定 / 沉淀
- 最终带来……

避免：

- 空泛口号
- “首先、其次、最后”式堆砌
- 只写做了什么，不写为什么做、结果如何
- 为了凑篇幅把同类动作拆成很多碎点
- 在 `S/T` 中重复价值观定义本身
- 一上来就写“本季度我重点践行了……价值观”且后文没有具体例子支撑

更自然的改写方向：

- 把抽象词换成场景词：`提升服务稳定性` → `处理线上问题、做稳定性治理`
- 把口号换成动作：`为用户创造价值` → `优先处理真正影响用户使用的问题`
- 把“完成任务”换成“落地结果”：`推进工作落地` → `尽量让问题真正解决、结果真正落下来`

## KR 与实际执行不一致时

如果实际工作与 KR 原文有调整，但实际产出更有价值，要客观写清楚：

- 先交代原 KR 目标是什么。
- 再说明执行中为何调整了治理范围或重点。
- 强调实际落地内容与核心目标的一致性，而不是回避变更。
- 语气保持客观，不写成“完全超出原规划”这种容易引发歧义的表述。

可参考表达：

- 实际执行过程中，结合线上问题优先级，对治理范围做了调整。
- 虽然与原 KR 中的表述存在一定差异，但实际落地内容更贴近本项工作的核心目标。
- 最终处理的事项数量或范围高于原计划，整体结果更具业务价值。

## 价值观自评写法

按下面的顺序组织内容：

1. 开篇点明本周期重点践行的价值观。
2. 选一个具体场景，交代背景与任务。
3. 写清“我”如何判断、补位、推动、协同或创新，突出与价值观定义相契合的行为。
4. 如有合适结果，简洁写出影响。
5. 最后说明该案例为何体现该价值观，并给出分数和等级。

重点：

- 例子要真实、具体，避免空泛表态。
- 行动与价值观的关联要自然，不要生硬上价值。
- 结果可以简写，但行动逻辑必须清楚。

常见价值观写法偏好：

- `用户导向`：强调“从用户实际感知和真实价值出发判断优先级”，不要只写“补功能”。
- `开放共赢-积极补位`：强调“在职责边界外主动补位，保障团队目标推进”。
- `以终为始`：强调“围绕最终结果倒推过程，不满足于动作完成”。
- `高效创新-敏捷迭代`：强调“快速响应、持续优化、让工作方式更高效”。

结合常见技术岗位素材，可优先这样落例子：

- `用户导向`
  - 高优先修复真正影响用户使用的线上问题
  - 资源链路从 `OSS` 调整为 `CDN` 全球加速，最终落点写“加载更快、体验更好”
  - 不只写“做了优化”，要写“用户侧具体变好了什么”
- `开放共赢-积极补位`
  - 主动把历史缺陷转到自己名下并持续跟进
  - 在某端问题修复中主动接手补位，减少积压和协作空档
  - 重点写“主动接住了什么”，不要只写“加强协作”
- `以终为始`
  - 不是只做分配到自己的问题，而是为了减少存量问题和后续影响，主动接手处理
  - 不是只做局部调整，而是围绕最终效果反推方案，例如为了提升加载速度而调整资源访问链路
  - 重点写“先想清楚最终要解决什么问题，再决定怎么做”
- `高效创新-敏捷迭代`
  - 通过补充内部工具能力或优化使用链路，减少重复性工作
  - 如果是个人维护的效率工具，不要把重点写成“推进某系统项目”，而是写“围绕日常使用中的实际问题补充能力”
  - 只有在用户明确想保留工具名时，再在 `A` 段自然带出“在某工具中新增了什么能力”

## 价值观举例速查表

当用户不知道“自己做过的什么事能算价值观”时，不要先讲概念，优先帮用户把实际工作往下面这些场景里对。

### `用户导向`

核心判断：

- 这件事是不是让用户用得更顺、更稳、更少出问题

常见可写例子：

- 修复高频线上 bug，减少用户使用阻塞
- 优先处理用户感知更明显、影响更直接的问题
- 优化上传、下载、页面打开、图片展示等链路
- 将资源访问方式从 `OSS` 调整为 `CDN` 全球加速，让资源加载更快
- 修复鸿蒙等兼容性问题，保障特定用户群体正常使用

适合落到结果里的词：

- 加载更快
- 使用更稳定
- 失败更少
- 体验更好
- 减少实际使用中的问题

### `开放共赢-积极补位`

核心判断：

- 这件事本来未必必须由我来做，但我主动接住了，避免团队节奏卡住

常见可写例子：

- 主动把历史缺陷转到自己名下并持续跟进
- 接手同事手上积压的一部分问题
- 在跨角色协作卡住时主动往前推动
- 某端问题没人接时先补上，保证事情继续推进
- 在任务衔接空档中主动承担排查、沟通、验证等工作

适合落到动作里的词：

- 主动接手
- 主动补位
- 持续跟进
- 协助推进
- 减少积压
- 避免事情卡住

### `以终为始`

核心判断：

- 不是只把事情做了，而是一开始就盯着最终结果，倒推怎么做

常见可写例子：

- 不只修单个 bug，而是顺手推动同类问题一起治理
- 不只做局部调整，而是围绕最终体验去优化整条链路
- 不只完成自己这部分，而是跟到问题真正闭环
- 先想清楚最终要解决什么问题，再决定方案和优先级
- 为了减少后续版本和协作成本，主动处理存量问题

适合落到表述里的句式：

- 先想清楚这件事最终要解决什么问题
- 不只停留在把事情做完
- 围绕最终效果推进
- 尽量让问题真正闭环
- 减少后续反复影响

### `高效创新-敏捷迭代`

核心判断：

- 这件事是不是让工作更省力、更顺、更快，而不是重复消耗

常见可写例子：

- 补充多语言管理、mock 数据维护等能力，减少重复操作
- 给内部工具增加便捷功能，让研发、测试更顺手
- 优化高频使用流程，降低人工维护成本
- 根据实际反馈快速补一轮功能或便捷性优化
- 发现团队常见低效点后，主动把链路补顺

适合落到结果里的词：

- 减少重复性工作
- 提升协同效率
- 降低人工维护成本
- 使用更顺手
- 更贴近日常场景

### 快速判断法

如果用户拿不准某件事算哪类价值观，可以先用下面几句判断：

- “这件事是不是让用户体验变好了？”
  - 通常偏 `用户导向`
- “这件事是不是本来不一定归我，但我主动接住了？”
  - 通常偏 `开放共赢-积极补位`
- “这件事是不是我先盯结果，再倒推过程怎么做？”
  - 通常偏 `以终为始`
- “这件事是不是让团队工作更高效、减少重复劳动？”
  - 通常偏 `高效创新-敏捷迭代`

### 技术岗位常见可写素材

用户给的事情如果落在下面这些类型里，通常都可以继续往价值观上归纳：

- 线上高频 bug 修复
- 历史缺陷治理
- 主动接手别人名下的问题
- 跨端兼容性修复
- 上传、下载、加载链路优化
- 服务稳定性治理
- 风险预警和提前处理
- 内部工具补能力
- 减少重复操作的流程优化
- 跨角色协同把问题闭环

如果用户没给完整案例，可以优先从这些常见场景切入：

- 线上问题治理
- 服务稳定性优化
- 交付风险预警
- 协作推进与问题补位
- 工具或流程优化带来的效率提升

## 评分与语气

评分口径优先以用户提供的标准为准；如果没有额外标准，读取 [score-and-style.md](references/score-and-style.md) 对齐常见写法。

- `1.0`：突出超额完成、远超预期、额外价值与显著结果，语气更自信。
- `0.7`：强调目标已完成、达到预期、行动有效，语气平实肯定。
- `0.5`：强调大部分达成，既写成果，也客观交代未完全闭环部分。
- `0.3`：强调仅完成部分内容，客观说明阶段性进展和差距，避免拔高。

## 风格要求

- 默认使用中文书面语。
- 保持专业、精炼、自然，避免明显的 AI 腔。
- 强调结果导向和主动性，但不过度包装。
- 尽量用因果关系把“目标、动作、结果、价值”串起来。
- 如果用户给了最终认可的范例，优先模仿其节奏、语感和收束方式。
- 默认按照“像自己写的季度自评”来收敛语气，不写成宣讲稿或价值观释义。
- 优先保留用户原句里的真实信息，再做压缩和顺句，不轻易替换成更空泛的表达。
- 对 `0.7` 这类“符合预期”口径，语气要平实，不要写成明显拔高的“超额达成”。

## 输出要求

- 默认直接输出可提交版本，不额外解释方法论。
- 如果用户只给原始要点，先整理逻辑再成文，不要照抄笔记。
- 如果用户要求“更像人写的”，优先压缩套话，增强动作与结果之间的因果表达。
- 如果用户给了固定格式或字段标题，严格按其格式输出。
- 如果用户要求简洁版，优先输出 STAR 短句，不主动扩写成长段。
- 如果用户提供了文档链接，按需自然插入正文，不单独堆在结尾。
- 如果用户需要“自评总结”，单独输出一段总评，不重复枚举每个 KR 细节。
- 如果用户已经给出一版草稿，默认先做“轻改版”，重点优化 `S/T` 的自然度、`A` 的具体性、`R` 的收束感。
- 如果用户连续多轮都在收短句，后续默认直接给“简短版本”，不要再同时给长短两版，除非用户明确要求。
- 如果用户指出某个事实表达不准确，例如“不是转过来，是我主动转到自己名下”，要优先修正事实，再润色语句。

## 常见改写偏好

- 优先保留真实动作：`主动将 6 个 bug 转到自己名下并持续跟进`
- 优先保留真实结果：`资源文件加载速度更快`
- 少写抽象目标：`提升价值、赋能协作、闭环落地`
- 多写具体感知：`减少积压、避免卡住、加载更快、协作更顺`

遇到下面情况时，优先这样处理：

- 用户说“太虚了”
  - 补具体例子，尤其是“谁的什么问题、我接了什么、带来什么结果”
- 用户说“AI 味重”
  - 先缩短 `S/T`
  - 去掉口号式前缀
  - 把概念词换成场景和动作
- 用户说“简洁一点”
  - 默认只给一版简短可提交版本
- 用户说“这个不是正式项目，只是提效工具”
  - 弱化项目名和“推进某系统”，强调“结合日常场景补充能力、提升效率”

## 快速检查

- 是否点明了目标，而不是只罗列事项
- 是否提炼出了 1-3 项关键动作
- 是否写清了完成情况和业务影响
- 是否与目标分数匹配，没有过度拔高
- 是否自然流畅，没有明显模板味
- 是否在结尾明确写出分数或等级
- 如果用户要求 STAR，是否真的输出了 `S/T/A/R`
- 如果用户要求简洁，是否控制住了篇幅
- 如果有文档链接，是否嵌入到了最合适的段落
- `S/T` 是否足够自然，读起来像本人复盘而不是模板套话
- `A` 是否写出了真实动作，而不是泛泛写“推进、协调、优化”
- `R` 是否收束到“实际效果 + 分数”，没有重复讲过程
